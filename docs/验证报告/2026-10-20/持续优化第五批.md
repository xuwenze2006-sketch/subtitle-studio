# 持续优化第五批：内容关联与人工修改保护

基线 `055e75f`。本批处理第 13–15 轮；审计、测试、构建和发布不另计轮数。全部复现使用临时合成文件、替代识别与翻译，不读取真实账号或用户媒体，不调用真实提供商。

## 第 13 轮：导入字幕绑定实际消费字节

旧流程先给 seed 算哈希，稍后重新读取并解析。在两步间改写等长文件并恢复 mtime，任务仍 complete，保存旧 seed 哈希却使用新正文；恢复原 seed 后还会复用错误结果。反例见忽略证据目录的 `seed-audit.log`。

现在第二次读取保留实际字节并同步计算 SHA；大小与原哈希一致后才解析该内存字节集。核对位于新 prepare/state、云配置和预算准备之前；块间检查取消。不增加第三遍内容读取。读取结束后的外部变化不会改变这份内存快照；下次仍按真实文件内容核验。

新增五项测试覆盖哈希后改写/替换、读取中变化、BOM/多行、取消与读后变化；独立审查未发现阻断问题。任务 identity 格式、已有 identity、时间戳兼容及缓存保持。

## 第 14 轮：Windows 时间刻度碰撞

本轮完整回归前的定向测试发现上一批的真实原生观察用例不稳定。独立重放八次，不同正文快速改写有五次返回旧摘要；直接 WinAPI 对照也出现写入前后 ChangeTime 相同。恢复 mtime 之前已经碰撞，不能把它归为测试慢或只加 sleep 消除红灯。

Windows 现在以仅共享读取的原生句柄保护输入与既有成片各自的单次哈希区间，再做前后观察。已有 writer/delete 访问时立即说明占用并拒绝，不降级为弱观察。正常读者兼容；读取、查询失败与取消都释放自有句柄，关闭错误保留原始异常。旧竞态用例现在证明写入/替换被阻止、原字节保留，并验证保护退出后恢复可写。

十二项独立原生保护用例覆盖普通读者、已有 writer/delete、hardlink 写入、Python 可写映射、关闭全部用户 file/mapping 句柄后仍存活的原生可写 view、异常和句柄清理。保护只覆盖哈希区间；不承诺整个媒体处理期间输入不可变，也不承诺其他平台的空上下文拥有同等原生保证。

## 第 15 轮：发布时保存人工修改

旧流程规划输出并保存恢复日志之后直接替换根字幕。独立编辑线程在日志已落盘的边界保存人工内容，旧程序随后 complete，人工文件和备份均找不到。单纯再算一次哈希仍有最终检查与替换之间的窗口。

本次仅对合并输出引入单文件发布模块。Windows 原生替换同时捕获实际被替换的文件对象；旧写句柄的迟写仍落入被保留对象。只有独占读取/删除句柄下核对为已知机器正文，才通过同一句柄删除旧版。变化或占用则保留原对象与恢复日志，显示路径并阻止成功结论。正常机器更新不逐代积累备份。此前不存在的目标使用不覆盖已有文件的发布；1177 等不确定部分失败保留证据，不盲目重试。

恢复日志升级为 version2 并兼容旧版。验证整批记录后才恢复；缺失目标的原对象恢复也不覆盖同时创建的新文件。发布冲突立即停止新调度。已经在途且经过来源/内容核验的结果仍可登记，原出版检查点保留，另存其后完成工作的检查点。双 worker 对照证明冲突后不提交第三段，人工处理后只识别剩余段，已完成的第二段不重复。

模块 23 项定向测试覆盖真实旧 writer、可写 view、hardlink、junction、部分失败、取消、暂时占用及准备失败清理；runner 四项覆盖实际编辑与恢复。最初集成测试暴露了继续调度导致检查点漂移，修复后才进入完整验证。POSIX 回退保留旧对象并要求核对，不自动删除可能仍有旧 fd 写入的版本；它不具备 Windows 的独占清理保证。

### 发生发布冲突后的处理

程序提示 `用户修改备份/发布恢复-<编号>`。其中 `previous.srt` 是实际被替换的对象，可能仍被编辑器写入；`replacement.srt` 是准备文件，部分操作完成后可能已经移走。根字幕可能已是程序的新输出，不能据此认为人工文本没有保留。

1. 让编辑器完成保存并关闭相关文件。把提示的整个恢复目录以及当前字幕另存到项目外的独立目录，保留所有原件。
2. 对照当前字幕和 `previous.srt`，明确选择保留的人工版本。不要把机器草稿当成人工验收结果。
3. 核对完成后，将提示的整个命名恢复目录移出项目，再继续。若该次是首次生成、没有根字幕的机器基线，还须把当前人工根字幕另存并移出，选择从已核验片段重新生成；不要伪造生成哈希。人工版本保留供对照。

程序不会替用户删除冲突备份，也不会自动合并来源不明的人工文本。本次用临时项目验证上述恢复路径，未宣称原生 GUI 或真实用户项目验收。

## 第三次五轮反思（第 11–15 轮）

这些轮次确实改善了停止响应、内容相同任务恢复、seed 来源关联和人工文件可恢复性；每项都有旧行为反例。也暴露了成本：第 13、14 轮修正了之前过强的内容关联与原生时间观察假设，先前全绿不足以证明没有竞态。不能把补救旧假设包装成全新的产品能力，也不应以测试数或轮数替代使用效果。

第 15 轮引入了本批主要复杂度。它的理由是已复现的人工文本丢失，并保留了单文件、单用途边界；没有重写通用原子 I/O、预算或调度框架。冻结后的小文件对照（每种 3 组、每组 20 次、每次一份约 9 KB 字幕和一次落盘日志）中，原发布中位 2.86 ms，新发布中位 43.91 ms，增加约 41 ms/文件。这是明确的数据保全成本，不是性能加速；不据此推算真实整片速度。正常对照没有备份累积。本批完整测试时间也由上一批约 243 秒增加到约 394 秒，包含新增用例、更多磁盘操作及运行环境差异，不能把总差值都归因于单项实现。

冲突后明确要求人工核对，避免自动迁移/合并进一步扩大语义风险。真实 v1 项目没有历史音频 SHA 与片段来源证据；本轮只调查并保留已有预览、下载、快照出口，没有开发未经需求证实的自动迁移。

接下来先完成这批发布与使用验证；不为了凑轮数继续添加边缘功能。若继续优化，应优先看真实任务耗时、人工恢复体验和可重复的失败证据。下一次反思在累计第 20 轮。

## 冻结验证与证据

冻结后的完整离线后端运行 **1,323 项，1,320 项通过、3 项 Windows 符号链接权限跳过**，测试耗时 393.670 秒、外层 394.19 秒。回环 HTTP **26 次通过**，外层 3.36 秒、真实提供商请求 **0**。冻结前后 **138 个 Python 源码与测试文件哈希一致**。三份独立审查接受最终边界，发布专项 27 项独立复核通过；差异空白检查及 **17 个精确暂存文件**公开内容扫描通过。

前端本批未改，本机沿用已有证据；发布 CI 再次执行完整前端测试、构建及产物一致性检查。对应提交、远端状态、CI 和主工作区同步的最终结果写入忽略目录 `release-receipt.json`，不在文档中预先声称远端成功。
